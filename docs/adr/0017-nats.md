# 0017. Run one NATS cluster, an account per application, nkey authentication

- **Status:** Accepted
- **Date:** 2026-10-28

## Context

The next project needs NATS with JetStream. More applications may follow, and
each should use NATS without seeing the others' subjects or streams, or being
able to exhaust their storage. Some clients sit outside the cluster: the
operator's own devices, and nothing else — no third parties, no browsers.

NATS has three ways to authenticate, and the choice decides who holds which
keys:

- **Static configuration** — accounts and users written into the server's
  config. A user can be an nkey, an Ed25519 key pair whose public half is all
  the server needs.
- **Operator mode** — a JWT trust chain: an operator key signs accounts, account
  keys sign users. Users never appear in the server's config, can expire, and
  can be issued by whoever holds an account's signing key.
- **Auth callout** — the server asks a service of ours to decide.

## Decision

**One three-member JetStream cluster, shared** — a platform add-on
(`gitops/platform/nats.yaml`), one member per node (ADR 0016).

**One account per application**, named after its namespace, with its own
JetStream quota (`max_file`, `max_mem`, `max_streams`). Accounts are NATS's
isolation boundary: subjects, streams and quotas are all per account, and
nothing crosses without an explicit export.

**Static configuration, every user an nkey.** The server's config holds public
keys only, so the whole tenant registry is ordinary, publishable YAML
([0012](0012-treat-the-repository-as-publishable.md)):

- An **application's** seed is generated in a pipeline, sealed into its own
  namespace and kept nowhere else.
- A **device's** seed is generated on the device and never leaves it; it is
  registered by committing its public key.

**From outside, WebSocket through the shared Gateway** —
`wss://nats.heptapedal.com`, TLS terminated by the existing wildcard
certificate, an `HTTPRoute` like any application's.

## Consequences

- **No key needs custody.** There is no operator or account signing key whose
  loss is unrecoverable or whose leak mints users. A lost seed is replaced by
  generating another and swapping one public key.
- **Every change is a commit, and takes effect without a restart.** The chart's
  reloader sends `SIGHUP`; measured against the rendered config, an added key
  connects immediately and a removed key's open connections are closed at the
  reload.
- **No expiry, and no delegation.** Credentials last until removed, and only a
  change to this repository adds one. Both are right for clients that are all
  the operator's own; neither would be for credentials handed to someone else.
- **The accounts list must never be empty of users.** With no users anywhere,
  NATS configures no authentication and accepts anonymous clients — through the
  route, from the Internet. A `SANDBOX` account holding the operator's laptop
  key keeps that from being one deletion away. Measured: anonymous clients are
  refused over both TCP and WebSocket.
- **`no_advertise` is load-bearing.** Without it the server hands clients its
  members' pod IPs as reconnect targets, unreachable from outside.
- **WebSocket constraints.** Cilium's listeners already enable the WebSocket
  upgrade, but the route's request timeout would default to Envoy's 15 seconds,
  so the route sets it to zero. The Load Balancer cuts TCP flows idle for ~300
  seconds (gateway.yaml), so `ping_interval` is 60 seconds.
- **Capacity.** Requested: 3 × (60m, 144Mi) for server and reloader — 180m and
  432Mi, provisional and near idle, against the ~670m / ~1Gi that ADR 0016 left.
  Volumes are 3 × 5Gi of block storage, about 1.5 USD/month.
- **Grafana Cloud container-hours.** Six more containers (server and reloader,
  three times) on top of ADR 0016's third node puts the cluster at roughly
  38,700 a month, over the 37,944 free. If that bills, the reloader is the
  cheapest three to drop: with a config checksum on the pod template, a key
  change becomes a rolling restart instead of a reload.

## Alternatives considered

- **Operator mode (JWT).** Earns its keep when credentials go to people other
  than the operator: expiry, revocation lists, and account owners issuing their
  own users. Here it would mean an operator key to keep offline forever and a
  signing step for every device, where an nkey only needs registering.
  Migrating later re-issues every credential — a handful of keys at this scale.
- **A Kubernetes controller that issues accounts and credentials** (community
  operators exist). Automatic, but unofficial, and it would sit on the
  authentication path holding the signing keys.
- **Auth callout with projected ServiceAccount tokens.** Applications would need
  no Secret at all: the callout verifies the Pod's token with a TokenReview and
  maps its namespace to an account. The right next step if onboarding becomes
  frequent; for now it is custom code on the authentication path.
- **A NATS server per application.** Isolation by construction, at three
  JetStream members per application. Accounts give the same separation for one
  set of pods.
- **Native protocol from outside.** Either a second Load Balancer (12 USD/month)
  or TLS passthrough by SNI — which needs NATS's `handshake_first` on every
  client and a `TLSRoute`, still experimental on this cluster.
